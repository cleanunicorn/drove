# Architect's Journal

## 2026-09-21 - Verify syntax/lint claims against the repo's pinned toolchain, not the sandbox default

**Proposal:** N/A — process correction on an existing proposal, not a new architectural change.

**Why now?** PR #79 ("Add a CI quality gate") cited `except psutil.NoSuchProcess, psutil.AccessDenied:` in `server_manager.py:156` as Python-2-style syntax that raises a `SyntaxError` under Python 3 and that `ruff` flags via rule `E999`. Neither is true for this repo. drove pins **Python 3.14** (`.python-version`, `DROVE_PYTHON ?= 3.14`, `ruff target-version = "py314"`, `mypy python_version = "3.14"`), and [PEP 758](https://peps.python.org/pep-0758/) (accepted for 3.14) legalizes unparenthesized `except A, B:` as `except (A, B):`. Verified directly: `.venv/bin/python3` (3.14.0rc2, this repo's own venv) parses the file cleanly, and `uv run ruff check src/drove/server_manager.py` reports "All checks passed!". The same pattern recurs in `proxy.py` (lines 340, 467, 483) and is valid there too. I nearly made the identical mistake independently this run — my first `ast.parse` used the sandbox's default `python3` (3.11), not the repo's pinned interpreter — before re-checking against `.venv/bin/python3`.

**Tradeoffs:** The mistaken example didn't invalidate the proposal's actual argument (no CI workflow runs `make lint`/`make typecheck`/`make test`; `release.yml` publishes on every push to `main` with zero test gate) — that gap is real and I found independent evidence for it (a clean `uv sync` + `pytest -q` fails at collection with a pydantic/typing error on 3.14, never caught because nothing runs it in CI). But an inflated or false "core command is completely broken" claim is exactly the kind of thing that erodes a reviewer's trust in the whole proposal once they check it themselves.

**Migration path:** Left a corrective comment on PR #79 rather than opening a duplicate CI-gate proposal. Did not open a new proposal PR this run — PR #77 (Backend adapter extraction, open since 2026-08-24) and PR #79 (CI quality gate, open since 2026-09-07) are both still open and unreviewed; adding a third unreviewed proposal on top would just grow the backlog rather than move anything forward.

**Lesson:** Before citing a "this doesn't parse" / "this fails lint" claim as evidence in a proposal, run it through the *project's own pinned interpreter and lint config* (`.python-version`, `ruff target-version`, the actual `.venv`), not whatever `python3`/`ruff` resolves to first in the sandbox — language versions change what's valid, and a wrong urgency claim is worse than no claim. Also: check open PRs for an equivalent proposal before drafting a new one — if 2+ Architect proposals are already sitting unreviewed, that itself may be the thing worth surfacing (approval bottleneck) rather than adding a third.
